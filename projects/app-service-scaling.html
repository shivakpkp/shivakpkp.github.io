TERRAFORM · POWERSHELL · AZURE / PUBLIC REPOSITORY

App Service Plan scaling automation

An end-to-end Azure project that provisions monitoring and automation with Terraform, then uses PowerShell runbooks to adjust App Service Plan capacity when demand changes.

TerraformPowerShellAzure MonitorAzure AutomationGitHub ActionsPythonDocker
01 / PROJECT OVERVIEW

What does this project do?

This project automates changes to the compute capacity of an Azure App Service Plan based on application demand. An App Service Plan provides the compute resources used by the applications hosted on it. The automation changes the plan’s pricing tier and size (SKU), such as moving from B1 to P1v3, rather than requiring someone to make the change manually in the Azure portal.

When CPU or memory usage triggers a configured Azure Monitor alert, an action group invokes an Azure Automation PowerShell runbook. The runbook evaluates the request and its safeguards before changing the plan. For scale-down requests, it checks recent metrics to confirm that usage is low enough before reducing capacity.

The goal is to make capacity adjustments repeatable and controlled: provide additional capacity when needed and reduce unnecessary capacity when conditions allow. The project brings together Terraform infrastructure provisioning, GitHub Actions delivery, PowerShell operational logic, and Python deployment verification.

02 / HOW IT WORKS

From infrastructure code to a scaling decision.

  1. Provision the automation infrastructure. Reusable Terraform modules define Azure Automation resources, runbooks, action groups and CPU/memory metric alerts. Remote state tracks the managed infrastructure.
  2. Deploy through GitHub Actions. Separate plan and apply jobs make infrastructure changes reviewable before deployment. Destroy planning supports controlled environment cleanup.
  3. Detect a capacity condition. Azure Monitor evaluates the configured metrics and sends a fired alert through its action group to the relevant runbook.
  4. Check before making a change. PowerShell evaluates resource selection, the current and target SKU, cooldown conditions and supported transitions. Scale-down also requires sufficiently low recent utilization. A resolved alert or an unnecessary change should not initiate another scaling operation.
  5. Apply and verify the result. When the conditions are satisfied, the runbook requests the SKU change and checks the resulting state. Its structured output distinguishes a completed change from a skipped operation.

Example from testing: a scale-up run changed a plan from B1 to P1v3 and verified completion. A later scale-down request was skipped because memory utilization did not satisfy the required low-usage condition. This demonstrates both the scaling path and the decision to leave capacity unchanged.

03 / THE CHALLENGE

Automate capacity changes without reacting blindly.

Changing a plan’s capacity is only one part of the problem. The automation also needs to decide whether a request is relevant, whether the target tier is supported, whether a recent change requires a cooldown, and whether reducing capacity is appropriate.

Because the plan supplies compute to its hosted applications, a scaling decision has to be evaluated at the plan level. The project therefore combines monitoring signals with explicit checks instead of treating every notification as an instruction to change capacity.

04 / MY CONTRIBUTION

Build the provisioning and operational workflow.

I used modular Terraform to define the automation infrastructure and GitHub Actions to manage its deployment lifecycle. I developed and refined the PowerShell scaling logic, connected it to Azure Monitor alerts, and tested scale-up and scale-down behavior against deployed Azure resources.

The project also includes Docker-based Python verification to check the deployed configuration. These checks are read-only; operational scaling behavior is validated separately through runbook execution.

05 / ENGINEERING DECISIONS

Make the behavior controlled and observable.

  • Reusable infrastructure: Terraform modules keep resource definitions consistent and separate configuration from implementation.
  • Controlled delivery: saved plans and separate apply jobs support reviewable infrastructure changes, with remote state shared across runs.
  • Scaling safeguards: tag-based selection, cooldowns, supported SKU checks and low-utilization checks constrain when changes are allowed.
  • Clear outcomes: no-op and skipped requests are distinguished from successful changes, and completion is checked rather than assumed.
  • Separate verification: read-only deployment checks inspect configuration without triggering capacity changes.
06 / OUTCOME

A complete infrastructure automation project.

The result is a deployed and tested workflow spanning infrastructure provisioning, CI/CD, monitoring, scaling decisions and verification. It demonstrates how Terraform and PowerShell work together: Terraform establishes the automation resources, while PowerShell handles runtime decisions and capacity changes.
